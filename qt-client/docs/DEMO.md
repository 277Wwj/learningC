# 演示：Windows Qt 客户端连接 Linux 服务端

本流程用于复现实验，预期结果来自当前服务端源码。将“预期结果”和“本次实际观察”分开记录；未运行的步骤不要标记为通过。

## 准备

先按 [README](../README.md) 在 Windows 构建客户端，或解压已经部署好运行库的发布包。Linux 上准备本仓库、C++ 编译器、CMake 和现有根工程要求的 GTest 开发依赖。根工程是 Linux 服务端，客户端是独立的 `qt-client` 工程。

在 Linux 仓库根目录执行：

```bash
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release --parallel
```

查看 Linux 的可达 IP，并记录为 `LINUX_IP`。这里的 `LINUX_IP` 是下列文字和命令中的占位符，需要手动替换，例如 `192.168.1.50`。Windows 与 Linux 不在同一网络时，应先由用户配置网络连通方式。客户端不会安装系统、修改防火墙或自动切换服务器进程。

Windows PowerShell 可检查端口是否可达：

```powershell
Test-NetConnection -ComputerName 192.168.1.50 -Port 8080
Test-NetConnection -ComputerName 192.168.1.50 -Port 12735
```

只检查已经启动的服务对应端口。端口不可达时，先核对 IP、进程监听地址和虚拟机端口映射。客户端中的 `127.0.0.1` 指 Windows 本机，不能自动指向另一台 Linux 机器。

## 实验一：单线程 HTTP

Linux 启动：

```bash
./build-release/webserver
```

选择“HTTP 请求”，输入 `http://LINUX_IP:8080/`，点击“发送请求”并查看状态码、响应头、正文和耗时。依次尝试：

| 路径 | 预期状态码 | 应关注的结果 |
| --- | --- | --- |
| `/` | 200 | 首页正文 |
| `/hello` | 200 | Hello 正文 |
| `/missing` | 404 | 收到了有效 HTTP 响应，不能误称网络连接失败 |

留存一张成功响应截图和一张 404 截图，记录客户端 URL 与 Linux 终端请求日志。实验结束后在 Linux 用 Ctrl+C 停止该进程，释放 8080。

## 实验二：线程池与慢请求

Linux 启动：

```bash
./build-release/webserver_thread
```

请求 `http://LINUX_IP:8080/slow`。超时设置为 5000 ms 时，预期约 2 秒后收到 200；端到端时间还包含网络和调度开销。响应头包含 `Connection: close`。

把请求超时改为低于 2 秒，再发送 `/slow`，观察超时提示、控件是否恢复，以及窗口在等待期间是否仍能拖动和操作。取消与超时是不同原因，应在记录中区别。恢复 5000 ms，再进行其他实验。

可用少量请求、并发 2 观察慢请求期间的调度。不要只凭一次 GUI 测量推断线程池性能提升幅度。结束后停止该进程再切换版本。

## 实验三：主从 Reactor 与测量边界

Linux 启动：

```bash
./build-release/webserver_multithread
```

分别请求 `/` 和 `/missing`。当前实现都返回 200 和固定正文，这是服务端没有区分路由；不能以第二个请求验证 404。

选择“轻量压测”，填写相同 HTTP URL，使用默认的 100 次、并发 4、每次超时 5000 ms，点击“开始测试”。观察进度和完成结果，通过“导出 CSV”保存结果，并记录：目标 URL、服务端版本、请求数量、并发、超时、连接模式、客户端/服务端机器与网络条件。平均值与 P50/P95 只统计完整成功的 2xx；吞吐量包含非取消的错误结果。

再用少量请求验证中途停止，确认停止后进度不再继续增加新请求，进行中的请求被取消，界面恢复可操作。停止发生时已经完成的请求仍属于本次结果，尚未发出的计划请求不能伪装成已完成。

当前测量逐请求创建新的网络管理器，使用短连接；GUI 和连接建立成本会影响数值。它用于观察客户端的任务调度和端到端表现。仓库根 README 的 wrk 数据是另一种工具、连接模式和测量条件，不能直接并排宣称孰优孰劣。

## 实验四：TCP 登录、名单和消息转发

Linux 在仓库根目录启动：

```bash
./build-release/chat_server
# 另开终端，可运行业务冒烟测试；不要同时混入其他已登录客户端。
python3 tests/chat_smoke_test.py
```

TCP 端口为 12735，与 HTTP 的 8080 不同，两者可同时运行。以下是依据当前源码制定的预期流程，尚不代表本次已完成真实 Linux 联调。

1. 打开两个客户端进程 A、B，在 TCP 页面输入 Linux IP 和 12735，分别连接。此时只代表 TCP 已建连。
2. A 选择 Login，填写 `alice`，发送完整帧。检查 RX 收帧记录中 Welcome 的昵称和 Users 名单。
3. B 以 `bob` 登录。检查两边收到的 Users 均包含 alice 和 bob。
4. A 选择 Say 广播，填写正文并发送。B 应收到 Chat，发送者为 alice；A 不会收到自己的 Chat 回显。
5. B 选择 Say 私聊，目标填写 alice，发送正文；A 应收到模式为 D 的 Chat。
6. 已登录连接再次发送 Login，应收到可恢复的 Error。测试重名则用第三个未登录连接输入 alice；被拒绝后可换昵称重试。
7. B 发送 Bye，服务端关闭 B；A 收到更新后的 Users。不要在连续两帧模式下发送 Bye 来验证两条业务处理，因为第一条已要求关闭连接。

发送方式也可选择“100 ms 分段”，在 Linux 日志核对最终解析的完整消息。测试“连续两帧”可对已登录 A 使用 Say 广播，由 B 核对收到两条 Chat；连续 Login 的第二条会得到重复登录错误。

TCP 不保证接收调用次数与写入次数一致。客户端 `TX queued` 只表示进入本地发送队列；Welcome 是登录回复，Chat 是实际收到的转发数据，客户端没有额外的送达/已读确认。发送后 1.5 秒未收到帧只提示，不自动关闭连接；广播发送者不收到回显不能当作发送失败。当前后端会清理长时间未收到数据的连接。

选择收帧记录查看字段与十六进制，使用“导出 JSON”保存记录，并对照 Linux 日志。非法帧、无响应和中途断线等客户端处理可由 `test_tcp` 验证；测试夹具结果与真实后端验证分开记录。

## 无 Linux 环境时的演示

仍可完成 Windows 编译、四套自动化测试、UI 操作和运行包启动检查。自动化测试可以通过本地受控服务验证客户端成功、错误、超时和协议处理。真实 Linux 互通应标记为“待在用户 Linux 环境复现”，不要把本地测试服务描述成已经部署的业务后端。

当前工作区的只读环境检查发现：`wsl.exe` 存在，但 `wsl --list --quiet` 返回“未安装适用于 Linux 的 Windows 子系统”；PATH 中未发现 Docker/Podman/虚拟机命令，常见 Docker、VirtualBox、VMware 安装位置也未发现对应命令。该检查不排除用户有未连接的远端 Linux 或其他位置的虚拟机，也不代表已经开展远端联调。
