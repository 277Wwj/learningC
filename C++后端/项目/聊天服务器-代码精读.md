## 0. 先看懂它在干嘛

一句话：**一个聊天"中转站"**。所有人只连它，它替大家转消息 —— 聊天双方不再需要互相能连上，各自能连到服务器就行（所以能跨网段、跨互联网）。

```mermaid
flowchart LR
    A["客户端 A"] -- "Login / Say / Bye" --> S[("chat_server :12735")]
    S -- "Welcome / Users / Chat / Error" --> A
    B["客户端 B"] -- "Login / Say / Bye" --> S
    S -- "Welcome / Users / Chat / Error" --> B
```

**一条数据在程序里的路线**（记住这条线，后面都好懂）：

```
epoll 说"fd 可读了"
  → onRead        收字节、把字节流切成完整帧
  → handleFrame   看类型，分派出去
  → handleLogin / handleSay / ...   查表，决定发给谁
  → sendFrame     进发送缓冲
  → flush         能发多少发多少；发不完就挂 EPOLLOUT 等续发
```

## 1. 协议速查（30 秒版）

帧格式：

```
 +--------+--------+--------+-----------+
 | 4B 长度 | 4B 魔数 | 4B 类型 |  payload  |
 +--------+--------+--------+-----------+
   大端序   0x4C434831          长度 = 4(魔数) + 4(类型) + payload 字节数
```

| 类型 | 值 | 方向 | payload 布局 |
| --- | --- | --- | --- |
| `Login` | 1 | C→S | 昵称（UTF-8） |
| `Welcome` | 2 | S→C | 你的昵称（登录成功） |
| `Users` | 3 | S→C | 全部在线昵称，`\n` 分隔（名单一变就推） |
| `Say` | 4 | C→S | `[1B 模式]['D' 时: 目标昵称+'\0'][正文]` |
| `Chat` | 5 | S→C | `[1B 模式][发送者昵称+'\0'][正文]` |
| `Bye` | 6 | C→S | 空 |
| `Error` | 7 | S→C | 错误文本（**致命**错误随后断开；**可恢复**错误只提示） |

两个比喻帮你记：

- **4B 长度前缀 = 快递单上的"总重"**：收件人先看总重，货不够就接着等（解决粘包/半包全靠它）。
- **`'\0'` 分隔符 = 小盒子上贴的"内件名"**：把"变长的昵称"和"变长的正文"切开。

## 2. 先认数据结构

| 表 | 键 → 值 | 比喻 | 用途 |
| --- | --- | --- | --- |
| `conns_` | `fd` → 连接 | **门牌号**（IO 世界的地址） | epoll 回来的是 fd，按 fd 找连接 |
| `nameIndex_` | `昵称` → `fd` | **通讯录**（业务世界的地址） | 私聊"发给小明"，按昵称找 fd |

两个小成员：

| 成员 | 作用 |
| --- | --- |
| `pendingReap_` | "待火化"队列：要关闭的连接先挂这里，等安全点统一销毁（见 3.15/3.16） |
| `usersDirty_` | "名单脏了"标记：谁上线/下线就置位，安全点统一广播一次名单 |

## 3. 逐函数精读

### 3.1 工具区（源码最上面的小函数们）

#### `setNonBlocking(fd)`

```cpp
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);
```

给 fd 加上非阻塞。**为什么必须要**：后面所有循环都靠"没数据了立刻返回 EAGAIN"来收尾（accept 循环、recv 循环、send 循环）。阻塞模式下随便读一下就把整个事件循环卡死。

#### `logLine(fmt, ...)`

带时间戳的日志，printf 风格变参，输出到 stderr。学习版够用；正式项目要换成异步日志（你的 `simpleLogger.hpp`），否则压测时日志能把性能拖垮。

#### `readBe32(p)` —— 收方向的"读一个数"

```cpp
uint32_t v = 0;
memcpy(&v, p, sizeof(v));
return ntohl(v);          // 网络序(大端) → 主机序
```

两个细节：
- 用 `memcpy` 而不是 `*(uint32_t*)p` 强转 —— 网络包内存不保证 4 字节对齐，强转在 ARM 上会崩；
- `ntohl` 把大端换成本机序，x86 上不做这步数字全是反的。

#### `packFrame(type, payload)` —— 发方向的"打包"

```cpp
const uint32_t bodyLen = 8 + static_cast<uint32_t>(payload.size());
frame.append(beLen,   4);    // 长度（大端）
frame.append(beMagic, 4);    // 魔数 0x4C434831
frame.append(beType,  4);    // 类型
frame.append(payload);       // 负载
```

#### `printable(s)`

打日志专用：不可打印字节（`\n`、`\0`、中文的每个字节……）统一换成 `.`，最多留 80 个字符。目的只有一个 —— **日志别被二进制刷屏**。

#### `isValidNick(nick)` —— 昵称的三道门

```cpp
if (nick.empty() || nick.size() > proto::kMaxNickLen) return false;
for (unsigned char c : nick)
    if (c < 0x20 || c == 0x7F) return false;   // 控制字符一律不要
return true;
```

重点防 `\n`：`Users` 名单用它当分隔符，昵称里混进换行，"名单"整个就串行了。

#### `buildChatPayload(mode, from, body)`

```cpp
p.push_back(mode);    // 'B' 或 'D'
p += from;            // 发送者昵称
p.push_back('\0');    // 分隔符
p += body;            // 正文
```

#### `onSigint` / `g_wakeupFd` —— Ctrl+C 的正确姿势

```cpp
void onSigint(int)
{
    const uint64_t one = 1;
    ssize_t n = ::write(g_wakeupFd, &one, sizeof(one));   // 只干这一件事！
    (void)n;
}
```

信号处理函数里只能调"异步信号安全"的函数（`write/read` 可以，`printf/malloc` 不行）。所以它只做一件事：**往 eventfd 写 1 个字节，把事件循环"戳醒"**；真正的收尾工作在 `onWakeup()`（3.18）里慢慢做。

### 3.2 `struct Connection` —— 一条连接的全部家当

| 字段 | 说明 |
| --- | --- |
| `fd` | 门牌号 |
| `channel` | 这条连接在 epoll 里的"代言人"（回调都挂在它身上） |
| `in` (Buffer) | 收缓冲：可能收到半个包，先攒着 |
| `out` (string) | 发缓冲：send 没发完的剩在这里，等 EPOLLOUT 续发 |
| `nick` | 登录后才有值；也是"我在名单里"的凭证 |
| `lastActive` | 最后一次有动静的时间，给"踢空闲"用 |
| `closing` | **正在送客**标记：所有回调看到它就立刻返回 |

> 所有权设计：连接对象由 `conns_` 里的 `unique_ptr` 持有；回调里只捕获**裸指针 + closing 标记 + 延迟回收** 三件套保命（3.15）。

### 3.3 `start(port)` —— 开局做 4 件事

1. **监听 socket**：`SO_REUSEADDR`（重启不用等 TIME_WAIT）→ `INADDR_ANY` → `listen` → 非阻塞；装进 `listenCh_`，注册 epoll。
2. **定时器**：`timerfd` 每 5 秒响一次 → `onIdleTick()` 扫空闲连接。
3. **信号唤醒**：`eventfd` + `SIGINT` 处理函数；顺手 `SIG_IGN` 掉 `SIGPIPE`（"往已关闭的 socket 写"别把进程打死）。
4. **安全点**：`loop_.setPostDispatch([this] { reapPending(); });`

⚠️ **最容易忘的一句**：

```cpp
listenCh_->enableReading();          // 只改了内存里的 events_
loop_.updateChannel(listenCh_.get()); // 这句才真的写进 epoll
```

`enableReading/enableWriting` 这类函数**只改内存**，不同步给 epoll 就"事件永远不来"。源码里这对调用到处成对出现，看到就默念一遍。

### 3.4 `run()`

打印启动信息 → `loop_.loop()` 一气跑到退出 → 退出后把还活着的连接挨个 `removeChannel + close`。因为此时循环已停、单线程操作，直接清是安全的。

### 3.5 `onAccept()` —— 照单全收

```cpp
while (true) {
    const int fd = ::accept(listenFd_, nullptr, nullptr);
    if (fd < 0) {
        if (errno == EAGAIN || errno == EWOULDBLOCK) break;  // 收完了，正常退出
        if (errno == EINTR) continue;                        // 被信号打断，重试
        ...
    }
    ...
}
```

- **为什么循环 accept**：一次事件可能有多条新连接排队（LT 触发时至少一条，但一次全取干净省事）；
- **为什么非阻塞**：靠 `EAGAIN` 判断"队列空了"，不然会卡在 accept 上；
- 每条新连接装 4 个回调：读 → `onRead`，写 → `onWrite`，错 → `closeConn`，挂 → `closeConn`；
- 回调用**裸指针**捕获（`raw`），安全靠 3.15 的延迟回收 + closing 标记。

### 3.6 `onRead()` —— 拆帧五步（第 2 课核心）

背景：TCP 是字节流，你 send 两条，对方可能一次收全（粘包），也可能收三次才全（半包）。所以收到数据后**必须循环切帧**：

```
① 连 12 字节包头都没凑齐 → 半包，等
② 校验长度字段（8 ~ kMaxPayload+8）→ 非法直接断开
③ 整帧没收全 → 半包，继续等
④ 凑齐了 → 取 payload、retrieve(frameLen) 消费掉
⑤ 交 handleFrame —— 注意它可能顺手关掉这条连接
```

两个防坑点：

- **校验长度**：有人塞个 `0xFFFFFFFF`，不校验就要傻等 4GB 数据（内存被打爆）；
- **`retrieve` 必须调**：消费掉已处理的字节，否则下一轮又读到同一条，死循环。

### 3.7 `handleFrame()` —— 一分钟看懂的小状态机

```cpp
switch (type) {
case proto::Login: handleLogin(conn, payload); break;
case proto::Say:   handleSay(conn, payload);   break;
case proto::Bye:   handleBye(conn);            break;
default:
    sendError(conn, "协议错误：不认识的消息类型", /*fatal=*/true);
}
```

状态机规则：**没登录只收 `Login/Bye`；登录后收 `Say/Bye`**。`Welcome/Users/Chat/Error` 是服务器→客户端的方向，客户端发过来就是"跑飞了"，按致命错误处理（发错误 + 断开）。

### 3.8 `handleLogin()` —— 第 3 课核心

四步走：

1. 已登录过？→ Error（**不断开**，多半是客户端 bug）；
2. 昵称不合法？→ Error（**不断开**，用户换个名字还能重试）；
3. 重名？→ Error（**不断开**，同上）；
4. 全过 → 登记两张表 + 回 Welcome + `usersDirty_ = true`：

```cpp
conn->nick          = payload;
nameIndex_[payload] = conn->fd;       // 第二张表：昵称 → fd
sendFrame(conn, proto::Welcome, conn->nick);
usersDirty_ = true;                   // 名单变了 → 安全点统一广播（含新人自己）
```

> 注意 `Error` 的两种用法：**可恢复**（重名、对方不在线）只提示；**致命**（协议错误）发完断开。这就是为什么 Error 的注释特意写了"分两种"。

### 3.9 `handleSay()` —— 第 4 课核心

payload：`[1B 模式]['D' 时: 目标昵称+'\0'][正文]`。

- **没登录就发言** → 致命错误（状态机不允许）；
- **模式 `'B'` 群发** → `broadcastChat()`，转给除自己外所有在线用户；
- **模式 `'D'` 私聊**：

```cpp
const size_t sep = payload.find('\0', 1);
const std::string target = payload.substr(1, sep - 1);
const std::string body   = payload.substr(sep + 1);

auto it = nameIndex_.find(target);            // 通讯录：昵称 → fd
if (it == nameIndex_.end()) {                 // 对方不在线 → 可恢复错误
    sendError(conn, "对方不在线：" + target, /*fatal=*/false);
    return;
}
auto cit = conns_.find(it->second);           // 门牌号：fd → 连接
if (cit == conns_.end() || cit->second->closing) {   // 防御性检查，正常到不了
    sendError(conn, "对方不在线：" + target, /*fatal=*/false);
    return;
}
sendFrame(cit->second.get(), proto::Chat,
          buildChatPayload('D', conn->nick, body));
```

一次哈希查表 + 一次哈希找连接就是"O(1) 路由"——不用遍历所有连接问"你是小明吗"。

### 3.10 `handleBye()`

```cpp
closeConn(conn, "客户端主动退出（Bye）");
```

一行。剩下的清理（摘两张表、广播新名单、从 epoll 摘掉、延迟回收）全在 `closeConn` 里统一做 —— **退出路径只有一条，才不会漏**。

### 3.11 名单与广播四兄弟

#### `loggedConns()` —— 快照

```cpp
std::vector<Connection*> v;
for (const auto& [fd, conn] : conns_)
    if (!conn->closing && !conn->nick.empty())
        v.push_back(conn.get());
return v;
```

**为什么要先拷贝成数组**：广播时 `sendFrame` 失败会顺手 `closeConn → erase conns_`，边遍历 `unordered_map` 边改它是 UB。先快照、再操作，最稳（`onIdleTick / onWakeup` 同理）。

#### `onlineNicks()` —— 组名单

所有已登录昵称按字典序排好，用 `\n` 连成一个字符串。排序是为了让每次推送顺序稳定（`unordered_map` 的遍历顺序本来不保证）。

#### `broadcastUsers()`

`loggedConns()` 拿快照 + `onlineNicks()` 组名单 → 挨个 `sendFrame(Users)`。**只在安全点被调用一次**（见 `reapPending`）。

#### `broadcastChat(sender, body)`

```cpp
const std::string payload = buildChatPayload('B', sender->nick, body);
for (Connection* c : loggedConns()) {
    if (c == sender) continue;     // 发送者自己不回显
    sendFrame(c, proto::Chat, payload);
}
```

### 3.12 `sendFrame()` / `sendError()`

```cpp
void ChatServer::sendFrame(Connection* conn, uint32_t type, const std::string& payload)
{
    if (conn->closing) return;
    conn->out += packFrame(type, payload);   // 先入"发送缓冲"
    flush(conn);                             // 再尽力立刻发
}
```

`sendError` 是它的小弟：

```cpp
logLine("[!] fd=%d 发 Error：%s%s", ...);
sendFrame(conn, proto::Error, text);
if (fatal && !conn->closing)
    closeConn(conn, "致命错误：" + text);
```

### 3.13 `flush()` —— 半写与 EPOLLOUT（第 5 课核心）

**背景**：`send()` 不保证全发出去 —— 内核发送缓冲满了，就只发一半，甚至直接返回 `EAGAIN`。聊天消息几十 KB 很正常，必须处理"发到一半"。

```cpp
while (!conn->out.empty()) {
    const ssize_t n = ::send(conn->fd, conn->out.data(), conn->out.size(), MSG_NOSIGNAL);
    if (n > 0) { conn->out.erase(0, n); continue; }          // 发出去多少删多少

    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        if (!conn->channel->isWriting()) {
            conn->channel->enableWriting();                  // 挂上"可写"订阅
            loop_.updateChannel(conn->channel.get());        // 同步给 epoll（不能忘！）
        }
        return;                                              // 剩下的等内核来叫
    }
    closeConn(conn, "send 失败");                             // 真错了才断开
    return;
}
// 全发完了：把 EPOLLOUT 摘掉
if (conn->channel->isWriting()) {
    conn->channel->disableWriting();
    loop_.updateChannel(conn->channel.get());
}
```

⚠️ **两个 LT（水平触发）相关的大坑**：

1. **发完必须摘 `EPOLLOUT`**：LT 下只要发送缓冲还有空位，"可写"事件就会一直响；不摘掉，事件循环被空转刷爆、CPU 打满。
2. **`enableWriting` 后必须 `updateChannel`**：只改内存不同步 epoll = 事件永远不来（和 `enableReading` 一个道理）。

> 配套的小改动：`include/Channel.hpp` 为此补了 `enableWriting() / disableWriting() / isWriting()` 三个方法 —— 框架能力不够用时就补框架，这也是"框架如何长出来"的第一手经验。

### 3.14 `onWrite()`

```cpp
void ChatServer::onWrite(Connection* conn)
{
    if (conn->closing) return;
    flush(conn);   // 内核说"可写了" → 把剩下的继续发
}
```

### 3.15 `closeConn()` —— 送客，不是当街砍人（延迟回收）

```cpp
if (conn->closing) return;    // 幂等
conn->closing = true;

// ① 清理"业务世界的地址"：不摘干净 = 幽灵用户！
if (!conn->nick.empty()) {
    nameIndex_.erase(conn->nick);
    conn->nick.clear();
    usersDirty_ = true;       // 名单少了人 → 安全点广播新名单
}

// ② 从 epoll 摘掉 + 关 fd
loop_.removeChannel(conn->channel.get());
::close(conn->fd);

// ③ 对象先不死！挪到"待火化"队列，等安全点再销毁
pendingReap_.push_back(std::move(it->second));
conns_.erase(it);
```

**为什么不当场 delete**：此刻可能正处在 conn 自己的回调栈里，而且本轮 epoll 返回的 ready 列表里可能还有别的 Channel 指向它 —— 当场 delete 就是 use-after-free（悬空指针）。

**幽灵用户**是什么：人已经下线，但 `nameIndex_` 里还留着他的名字 → 别人私聊他"能发出去"、名单越列越长。所以关闭和登录必须**成对维护两张表**。

### 3.16 `reapPending()` —— 安全点，干两件事

```cpp
if (!pendingReap_.empty()) {
    pendingReap_.clear();     // ① 本轮所有回调都返回了，放心销毁
}
if (usersDirty_) {
    usersDirty_ = false;
    broadcastUsers();         // ② 名单变过 → 统一广播一次
}
```

**为什么名单广播要拖到这里**：如果"谁登录谁立刻广播"，广播里 `sendFrame` 失败又会 `closeConn` → 又触发广播……层层嵌套调用（重入），很容易写出难查的 bug。延迟到安全点、一次播完：因为**一轮事件全处理完时做收尾，永远不会踩到别人的栈帧**。

### 3.17 `onIdleTick()` —— 踢空闲

先收集（`vector<Connection*> dead`）再处理（`closeConn`）—— 因为 `closeConn` 会改 `conns_`，不能边遍历边改。

> 现在是"120 秒没收到任何数据就踢"。更正统的是协议层心跳（Ping/Pong），等接 Qt 客户端时再升级。

### 3.18 `onWakeup()` —— Ctrl+C 收尾

```cpp
ssize_t n = ::read(g_wakeupFd, ...);         // 把 eventfd 读掉
for (Connection* c : all)                    // 挨个通知
    sendFrame(c, proto::Error, "服务器正在关闭");
loop_.quit();                                // 退出事件循环
```

### 3.19 `main()`

```cpp
ChatServer server;
if (!server.start(proto::kPort)) return 1;
server.run();
return 0;
```

## 4. 四个"为什么"（面试考点速答）

**Q1：为什么连接对象不当场 delete？**
A：回调执行时可能还在 conn 自己的调用栈上，且本轮 epoll 的 ready 列表里还有别的 Channel 指向它。当场 delete 就是 use-after-free。做法：标记 closing + 从 epoll 摘掉 + 挂进待回收队列，在"本轮所有回调都返回后"的安全点统一销毁。

**Q2：为什么要维护两张表，还都得清？**
A：fd 是 IO 世界的地址（epoll 给的），昵称是业务世界的地址（私聊要用的）。`conns_` 管"怎么发"，`nameIndex_` 管"发给谁"。任何一边失效必须同步清另一边，漏了就是幽灵用户 / 野指针。

**Q3：为什么 `flush` 发完要立刻 `disableWriting`？**
A：我们跑的是 LT（水平触发）：只要发送缓冲有空位，"可写"事件会一直响。发完了不摘 EPOLLOUT，事件循环每轮都被叫醒 → 空转、CPU 打满。而在等的期间必须订阅它，否则"缓冲腾出来了没人通知"→ 消息卡死在 out 里。

**Q4：为什么名单广播放在安全点，而不是谁变谁立刻播？**
A：广播本身会 `sendFrame`，失败会 `closeConn`，`closeConn` 又要广播新名单 —— 递归重入。用 `usersDirty_` 打标记、安全点里一次播完，干净且高效（同轮 N 个人上下线也只播一次）。

## 5. 怎么测

### 5.1 最快的手动测试（nc）

服务器启动后会打印一条命令，粘一个"Login（昵称 hi）"帧过去：

```bash
printf '\x00\x00\x00\x0a\x4c\x43\x48\x31\x00\x00\x00\x01hi' | nc 127.0.0.1 12735
```

服务器日志会打出 `用户上线：hi`。

### 5.2 完整冒烟测试（推荐）

```bash
# 终端 1：跑服务器
./src/chat_server
# 终端 2：跑测试
python3 tests/chat_smoke_test.py
```

8 个场景覆盖：登录/名单广播、重复登录、第三人上线、重名重试、**慢客户端 6MB 洪泛不丢消息**、群发/私聊/对方不在线、未登录被断开、Bye 退出 + 幽灵用户检查。

### 5.3 验证 EPOLLOUT 续发路径真的被用过

```bash
grep '发送缓冲满' /tmp/chat_server.log | head   # 出现过 = 半写续发真的触发了
```

原理：测试洪泛总量 6MB，超过本机 `/proc/sys/net/ipv4/tcp_wmem` 上限（4MB），必然逼出 `EAGAIN` → 走 EPOLLOUT 续发。

### 5.4 常见小坑

- **bind 失败（Address already in use）**：旧服务器还在跑。用 `ss -ltnp | grep 12735` 找 PID，或者 `pkill -x chat_server` 清掉。**别用** `pkill -f '...c++...'` —— `+` 是正则元字符，匹配不到进程，会"看起来杀了其实没杀"。
- **想看事件循环调用链**：`TRACE=1 ./src/chat_server` 启动。
