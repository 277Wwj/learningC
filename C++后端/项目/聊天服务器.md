# 聊天中转服务器（Chat Relay Server）

> 把《11_lan_chat 局域网聊天》从「只能同网段」升级成「能跨互联网」：
> 用自研 Reactor 框架（[[EventLoop]] / [[Poller]] / [[Channel]] / [[Buffer]]）
> 写一个中心服务器，所有客户端都连它，由它转发消息。
>
> **简历上两条线合成一条**：C++ 服务端（epoll/Reactor）+ Qt 客户端。
> 关联笔记：[[WebServer]]、[[粘包与半包]]、[[select-poll-epoll]]、[[主从Reactor]]
> 逐函数代码精读（2026-10-09 完成）：[[聊天服务器-代码精读]]

## 一、为什么必须加中心服务器

原来的做法是 UDP 广播发现：

```
客户端 A  --广播-->  [整个局域网]  <--广播--  客户端 B      ✅ 同网段能用
客户端 A  --广播-->  ✗ 被路由器挡掉 ✗  <--广播--  客户端 B    ❌ 跨网段 / NAT 就废了
```

两个原因：

1. **广播不能跨网段**：路由器默认不转发 255.255.255.255，公共 Wi-Fi 还会做客户端隔离。
2. **NAT 挡在外面**：就算你知道对方公网 IP，人家家里那台机器在路由器后面，你连不进去
   （除非做端口映射或者 NAT 打洞）。

商业 IM 的解法就是**中心服务器**：所有人只跟服务器建立连接，服务器负责转发。
客户端不再需要知道对方的 IP——它只需要知道**服务器**的 IP。

## 二、架构

```
                （公网 / 任意可路由的网络）
                      ┌───────────────────────────┐
   Qt客户端 A ──────► │   chat_server : 12735     │ ◄────── Qt客户端 B
   （任意网络）        │   epoll + Reactor         │
                      │                           │
                      │  conns_  : fd   → 连接     │
                      │  nameIndex_ : 昵称 → fd    │
                      └───────────────────────────┘
```

**核心数据结构是两张表**（这是和 WebServer 最大的不同）：

| 表 | 键 → 值 | 用途 |
| --- | --- | --- |
| `conns_` | `fd` → `Connection*` | IO 层：epoll 回来的是 fd，按 fd 找连接 |
| `nameIndex_` | `昵称` → `fd` | 业务层：要发给「小明」，按昵称找 fd |

> 面试点：**fd 是 IO 世界的地址，昵称是业务世界的地址。** 服务器要干的就是维护这两张表的映射，
> 表里任何一项失效（断线、改名、被踢）都要同步清理——漏一个就是野指针或"幽灵用户"。

## 三、协议设计 v2

**帧格式和 Qt 客户端完全一致**（这点很重要：老代码里的拆包/组包逻辑可以直接复用）。

```
 +--------+--------+--------+---------------+
 | 4B 长度 | 4B 魔数 | 4B 类型 |    payload     |
 +--------+--------+--------+---------------+
   大端序    0x4C434831         长度 = 4(魔数) + 4(类型) + len(payload)
```

长度字段 = **它自己之后的所有字节数**。收方先读 4 字节就知道整条消息多长 → 解决粘包/半包。

| 类型 | 值 | 方向 | payload 布局 |
| --- | --- | --- | --- |
| `Login` | 1 | C→S | 昵称（UTF-8） |
| `Welcome` | 2 | S→C | 你的昵称（登录成功） |
| `Users` | 3 | S→C | 所有在线昵称，`\n` 分隔（名单一变就推送） |
| `Say` | 4 | C→S | `[1B 模式][ 'D' 时: 目标昵称 + '\0' ][正文]` |
| `Chat` | 5 | S→C | `[1B 模式][发送者昵称 + '\0'][正文]` |
| `Bye` | 6 | C→S | 空（主动退出） |
| `Error` | 7 | S→C | 错误文本，服务器随后断开 |

- **模式字节**：`'B'` = 群发（broadcast），`'D'` = 私聊（direct）
- **正文用 UTF-8**：中文一个字 3 字节，所以**长度必须按字节算**，不能按字符算
- **昵称用 `'\0'` 结尾**：因为后面的正文长度可变，需要一个分隔符把"变长的昵称"和"变长的正文"切开

> 面试点：自定义协议怎么让双方都不歧义？答案是**要么有长度，要么有分隔符，要么定长**——
> 这三种之外没有第四种。我们这里是混合用：整体用长度，内部可变字段用 `\0`。

## 四、和 [[WebServer]] 项目的区别（面试对比着讲）

| 维度 | WebServer | 聊天服务器 |
| --- | --- | --- |
| 协议 | 现成的 HTTP（有标准） | **自己设计**应用层协议 |
| 连接状态 | 无状态（读完请求→回响应） | **有状态**（要记住"你叫什么"） |
| 数据方向 | 客户端发起，服务器被动响应 | **服务器主动推送**（别人发消息要推给你） |
| 核心难点 | HTTP 解析、keep-alive | **对象生命周期** + 连接间转发 |
| 数据结构 | `fd → Connection` 一张表 | 两张表（fd↔昵称 双向索引） |
| 定时任务 | 超时断开 | 超时断开 **+ 心跳保活** |
| 发送 | 响应短，一次 `send` 基本够 | 要处理**半写**（发送缓冲 + EPOLLOUT） |

## 六、体检报告：现有框架的 5 个缺口

> 这部分是**最值钱的学习材料**——"框架原来长这样，做新需求时发现不够用，我改成了这样"，
> 比"我照着教程抄了一个服务器"强一百倍。

### ① `Trace` 在热路径上打印 `stderr`（已修 ✅）

`Poller::poll`、`Channel::handleEvent` 每次事件都 `fprintf(stderr, ...)`。
一个聊天服务器每秒几千个事件，日志直接刷屏，而且 `fprintf` 是很慢的 IO。
**修法：改成环境变量开关，默认关闭，`TRACE=1 ./chat_server` 时才打印。**

### ② `EventLoop` 没有"安全点"（已修 ✅）

```cpp
for (auto &[ch, revents] : ready) ch->handleEvent(revents);
// ↑ ready 里存的是裸指针。如果 A 的回调把 B 的连接关掉并 delete，
//   而 B 恰好也在 ready 里，下一轮循环就是 use-after-free
```

**修法：加 `setPostDispatch()`，在一轮事件全部分发完之后统一回收对象。**
（这就是 [[WebServer]] 里记的坑 #4「不能在 Channel 自己的回调里 delete 自己」的系统性解法。）

### ③ `Channel` 只有 `enableReading()`（已修 ✅ 2026-10-09）

没有 `enableWriting()` / `disableWriting()`，`handleEvent` 里虽然有 `EPOLLOUT` 分支，
但没有任何办法把 `EPOLLOUT` 加进 `events_`。
**已补齐**：新增 `enableWriting() / disableWriting() / isWriting()`，
chat_server 的 `flush()` 已在用（发不完挂上、发完摘掉），6MB 洪泛实测触发续发。
而且 `enableReading()` / `enableWriting()` **只改内存里的 `events_`，不会自动 `epoll_ctl`**，必须手动
`loop.updateChannel(ch)`——漏一次就是"事件再也不来了"。

### ④ `Buffer` 没有 `append` / 没有"可写"语义 ⬜ 第 5 课修

- `append` 是 `private`，服务器想自己往缓冲里放数据不行
- `readFd` 对「对端关闭」和「读错误」都返回 `-1`，分不清（不影响正确性，但没法打日志区分）
- 没有 **output buffer** 的配套操作（发送缓冲要支持"没发完的部分留着，等 EPOLLOUT 续发"）

### ⑤ ⚠️ README 说 "ET 边缘触发"，但代码里根本没有 `EPOLLET`

`grep EPOLLET include/` → 0 条。`Channel::enableReading()` 只 `|= EPOLLIN`，
**实际跑的是 LT（水平触发）**。

这件事必须处理，因为它是个**会被面试官抓的硬伤**：

- 诚实的做法有两个：
  - **A（推荐，成本低）**：把 README 里的 "ET" 改成 "LT"，并在面试时主动解释
    "我选 LT 是因为……"。LT 更简单、更不容易漏事件，聊天这种低频场景完全够用。
  - **B（成本高）**：真的加上 ET——`events_ |= EPOLLIN | EPOLLET`，并确保
    **所有 fd 都非阻塞 + 每次都读到 EAGAIN**（`Buffer::readFd` 和 accept 循环恰好已经这么写了，所以改造难度不大）。
- 千万**不要**什么都不改。面试官问一句"你 ET 怎么保证读干净的"，答不上来就全塌了。

## 七、第 7 课验收：压测与内存检查（2026-11-06）

> 工具：`tests/bench_chat.py`（压测客户端）、`tests/bench_compare.py`（对比编排）、
> `tests/bench_min.py`（54 行极简版，用于对照理解）。
> 环境：5 核 Linux 虚拟机，Release 构建，`CHAT_LOG=0`（必须关日志，否则测到的是 `fprintf` 的速度）。
> 压测端 4 进程：单个 Python 事件循环只能推约 5 万条/秒，一个进程压不满 C++ 服务端。

### 7.1 承载能力：1000 连接

| 指标 | 数值 |
| --- | --- |
| 连接数 | 1000（4 进程 × 250） |
| 发送 QPS（`--mode ping`） | **198,764** |
| 服务端 CPU | 64%（3 个热线程，主从确实用上了多核） |
| 内存（RSS） | 空载 3.6 MB → 1000 连接 **23.4 MB**，约 **23 kB/连接** |

**23 kB/连接**是个值得记住的数字：如果实现成"每连接预分配 64 KiB 读缓冲"，
1000 连接就是 64 MB，10000 连接直接爆。这里的 `Buffer` 是按需增长 + 用完收缩，
所以真实占用远小于协议上限（`kMaxPayload = 64 KiB` 只是"单帧"的护栏，不是每连接的常驻开销）。

### 7.2 广播扇出：1000 人群发

| 指标 | 数值 |
| --- | --- |
| 投递 QPS | **381,108 帧/秒** |
| 延迟 P50 / P99 | **755 ms / 1595 ms** |
| 服务端 CPU | 89.5%（3 个热线程） |

一条 `Say` 扇出给其余 999 个连接 → 单条消息要触发 999 次 `sendFrame`，
**扇出量是 $O(N)$、但常数很大**。1000 人时 P99 到 1.6 秒，说明"广播风暴"是这个架构的
第一个真实瓶颈（见 §八 问题 ①）。

### 7.3 内存检查：ASan / UBSan / LSan 全通过

| 检查 | 结果 |
| --- | --- |
| ASan（越界 / use-after-free） | **0 错误** |
| UBSan（未定义行为） | **0 错误** |
| LSan（内存泄漏） | **0 泄漏** |

- 编译：`g++ -std=c++17 -O1 -g -fsanitize=address,undefined -I include src/chat_server.cpp -o chat_asan -pthread`
- 负载：冒烟测试 8 场景 + 300 连接 private + 300 连接 rtt + 退出时的批量 `closeConn` / 延迟回收路径。
- **做了正对照**：故意 `new int[100]` 不释放，确认 LSan 能报出 `Direct leak of 400 byte(s)`。
  所以"0 泄漏"是可信的结论，不是"工具没生效"。

> 注意：valgrind 也能用（本机已装），但 ASan 更快、能顺便查未定义行为，且对多线程更友好。
> 两者都不需要在源码里插桩，属于"零成本验证"。

### 7.4 单线程 vs 主从 Reactor 对照（同一份代码只改 `SUB_LOOPS`）

| 对比项 | 单线程 | 主从 | 怎么解读 |
| --- | --- | --- | --- |
| HTTP `wrk -t4 -c1000` | 5.0 万 QPS，单核 79% CPU | **8.9 万 QPS**，4 线程共 123% CPU | 单核已经打满，主从兑现成 **1.8 倍**吞吐 |
| 聊天 `private` 96 连接 ×1000 条 | 16.0 万条/秒，服务端 27% CPU | 18.6 万条/秒，3 线程共 38% CPU | 提升有限：单核只用了 1/4，**压测端（~100% CPU）才是瓶颈** |
| 聊天 `rtt` 32 连接乒乓 | P50 1.17 ms | P50 1.38 ms | 跨线程投递（`runInLoop` + 锁 + eventfd）的真实代价 **≈ 0.2 ms** |

两条结论：

1. **主从不总是更快**。每条私聊多一次跨线程投递，服务端 CPU 从 27% 涨到 38%、
   延迟涨 0.2 ms。只有单核真被打满时才会兑现成吞吐；否则只是白烧 CPU。
2. **压测工具本身也是被测对象**。修掉压测端三个 bug（热路径套 `asyncio.wait_for` 建定时器、
   每帧拼长字符串、每帧调 `time.time()`）后，投递 QPS 从 12 万涨到 18.6 万 ——
   之前"主从没提升"有一部分是测量误差。

### 7.5 简历可用的四个数字

```
1000 并发连接，198k QPS（心跳模式），服务端 CPU 64%，内存 23 kB/连接
1000 人群发扇出 381k 帧/秒，P50 755 ms / P99 1.6 s
```

## 八、第 7 课挖出的两个真问题（待修）

> 这两个比"功能做完了"值钱 —— 面试问"你遇到过什么困难"，这就是标准答案。

### ① 广播是同步扇出，1000 人时 P99 到 1.6 秒

`broadcastChat()` 把"发给某个 loop 的全部连接"投递成任务，接收方 loop 拿到任务后
**在同一个回调里遍历自己负责的所有连接逐个 `sendFrame`**（内部直接 `send()`）。
1000 人 → 单条消息 999 次 `send()`，发送者的 loop 要等全部投递完才回来处理下一条。

**方向**：把"分发"和"IO"解耦 —— 接收方 loop 只把帧 `append` 进各连接的发送缓冲
（纯内存操作），真正的 `send()` 交给各自的 `EPOLLOUT` 写事件去做；或者按 loop 分批、限流。

### ② "只收不发"的用户 69 秒被误杀

实测：客户端 A 只收不发（能正常收到别人的群发），客户端 B 每 15 秒发一次。
结果 **A 在 69 秒时被"空闲超时"踢掉，B 存活**。

原因在 [chat_server.cpp](../../src/chat_server.cpp) 的 `onIdleTick()`：

```cpp
if (now - conn->lastActive > kIdleTimeoutSec)   // lastActive 只在 onRead 里更新
    dead.push_back(conn.get());
```

`lastActive` 只在**收到数据**时更新，而"收到数据"不是"连接有效"的充要条件。
所以"一直在线看群但从不发言"的用户会被当成死连接。

**方向**：`lastActive` 在**发送成功**时也更新；或区分"读空闲"（判断协议层是否需要探活）
和"连接活跃"（判断 TCP 是否还有效）。这也正是为什么需要**单向心跳**：
`heartbeat_test.py` 场景⑤验证了服务器绝不主动发 Pong ——
旧客户端收到未知类型的帧会直接断开，所以心跳必须单向。
